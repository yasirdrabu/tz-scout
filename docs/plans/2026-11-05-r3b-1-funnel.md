# R3b-1 Funnel by source and cost per win Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show how far each source's accounts got and what each won account cost: the Funnel screen, its per-source drill, the Costs tiles Cost per account sent, Cost per won account and Return on spend, and the "Cost by source" table. The Sources page counts the same way.

**Architecture:**
- **Analytics** gains a journey read model: one row per account, filled from events. It records the account's first source and batch, when it entered each stage, whether it left, and its deals.
- **Backfill:** a CLI fills journeys for accounts that existed before the consumers, through small read functions exported by intake, routing, crm and accounts.
- **Pure functions:** the funnel, the costs and the insight line are pure functions over journeys and cost lines, so the APIs only load data and call them.
- **Costs:** cost lines gain a `source_id`. Usage from intake's own AI calls carries the arrival's source, and manual lines may name a source.
- **Sources page:** `/sources/stats` is computed from journeys in the route layer, so intake never imports analytics.

**Tech Stack:** TypeScript, Hono, Drizzle + Postgres (RLS, one database per workspace), outbox + NATS, React 19 + TanStack Query, vitest, msw, Playwright.

**Spec:** `docs/spec/analytics/account-funnel-by-source.md`, `docs/spec/analytics/source-performance.md`, `docs/spec/analytics/cost-ledger.md` (allocation), `docs/spec/analytics/index.md`, `docs/spec/analytics/access-and-exports.md`, `docs/spec/web-ui/screens.md` §10, §11 and §16-18, `docs/spec/web-ui/api-gaps.md` (Decision 26, rows 1086-1104). Code map: `docs/plans/2026-11-06-r3b-funnel.map.md`. R3b-2 (source trust) is a separate plan.

## Product decisions (user, 2026-11-05)

1. **Return on spend** uses actual won deal amounts. A won deal with no amount counts as won but adds no value.
2. **Target cost per won account** is one workspace setting, edited on Costs by `budgets:write`, with no default. With no target, cells have no colour and read "No target set".
3. **First source everywhere.** The Funnel and the Sources page both count an account under the source that first sent it, at the furthest stage it reached, so two screens never show two different Won counts.
4. **Source trust feeds scoring** (R3b-2, not here).

## Rulings (controller, 2026-11-05)

1. **Journey read model** (analytics; RLS on both tables):
   - `analytics.journey(tenant_id, account_id pk, first_source_id, first_batch_id null, arrived_at, practice_id null, offer_id null, exit_stage null, exit_at null, updated_at)`.
   - `analytics.journey_stage(tenant_id, account_id, stage_key, entered_at)`, with primary key (tenant, account, stage_key). It keeps the **earliest** `entered_at` seen, so a late or retried event never moves it.
   - `analytics.journey_deal(tenant_id, account_id, system, deal_external_id, status, amount_cents null, closed_at null, observed_at)`, with primary key (tenant, system, deal). A row only takes an event with a later `observed_at`.
2. **Consumers** (analytics):
   - **`intake.arrival.resolved`:** creates the journey if missing, or keeps whichever arrival is earlier by the event's `occurredAt`.
     - `first_source_id` is the chain's agent, else person, else vendor source, the same rule as `arrival.closest_source_id`.
     - `first_batch_id` is the event's `batchId`, and `arrived_at` is the event's `occurredAt`.
   - **`routing.stage.changed`:** records `to`'s entry at the event's `occurredAt`.
     - When `to` is an exit stage, it also sets `exit_stage` and `exit_at`, if the event is later than the stored `exit_at`.
     - When `to` is a flow stage later than the stored exit, it clears `exit_stage`.
     - Stage kinds come from routing's `listStages`.
   - **`scoring.account.scored`:** sets `practice_id` and `offer_id = bestOfferId`.
   - **`crm.deal.changed`:** upserts `journey_deal`.
   - **`accounts.account.merged`:**
     - The survivor keeps the earlier arrival (and its first source and batch).
     - It takes the minimum of each stage entry and the merged account's deals.
     - The merged account's journey is deleted.
   - A stage or deal event for an account with no journey yet still stores its rows. The journey row comes when the arrival does.
3. **Reached, won, assigned, lost** (pure, over the workspace's current stage list):
   - **Reached:** an account reached flow stage *k* when it has an entry for any flow stage at position ≥ *k*. A skipped stage counts as passed. Every journey has reached the first flow stage.
   - **Won:** reached the last flow stage.
   - **Assigned:** reached any stage that routing's `routingFunnelStages` marks `assigned`.
   - **Lost at a stage:** its furthest flow stage is that stage and `exit_stage` is set.
   - **Stage lists:** deleted stages are ignored, and the columns are the current flow stages in order.
4. **Attribution and roll-up.**
   - An account belongs to its `first_source_id`.
   - A source's numbers include accounts first-sourced from it **or any source below it** in the source tree. Removed sources are skipped.
   - The Funnel table lists **top-level sources** (no parent) with at least one account in the cohort. The drill, the Sources page and the source page work for any source.
5. **Period.**
   - `period` is one of `30d`, `90d` (the default), `quarter` or `year`. The quarter and year are calendar ones, in the tenant timezone, up to now.
   - **Cohort:** the accounts whose `arrived_at` falls in the period.
   - **Spend:** the cost lines whose `occurred_on` falls in the period.
   - **Filters:** `practice`, `offer` and `batch` narrow the cohort by `practice_id`, `offer_id` and `first_batch_id`.
   - **Sources page:** keeps "All time" (no period).
6. **Spend per source.** Only non-voided lines count.
   - A line with a `source_id` belongs to that source.
   - Otherwise a line with an `account_id` belongs to that account's `first_source_id`.
   - Otherwise it is **Shared costs**, which count in totals only.
   - **Roll-up:** a source's spend rolls up like its accounts (Ruling 4), and the per-source spends plus Shared costs equal the ledger total for the period.
7. **Cost lines get a source.**
   - **Column:** `analytics.cost_line.source_id null`.
   - **Usage event:** `integrations.usage.recorded` gains optional `sourceId`, and `CallOpts` gains `sourceId?`. Intake's arrival normalise call passes the arrival's closest source, and CSV column mapping passes the import's source.
   - **Manual lines:** `POST` and `PATCH /costs/lines` take an optional `source_id`; an unknown or removed source is refused with 400 "Choose a source that exists." The lines list returns `source_id` and `source_name`.
8. **Target.**
   - **Storage:** `analytics.cost_setting(tenant_id pk, target_cost_per_won_cents bigint null, updated_by, updated_at)`.
   - **API:** `PUT /api/v1/costs/target` `{ target_cost_per_won_cents: number | null }` (`budgets:write`, people only). Below 1 is refused with 400 "Enter a target above zero, or clear it."
   - **Reading it:** the target comes back in `/costs/summary` and in the funnel responses.
9. **Cost per won status** (pure `costStatus(sent, won, costPerWonCents, target)`), checked in this order:
   - `not_enough_data` when sent < 10;
   - `no_wins` when won = 0;
   - `no_target` when there is no target;
   - `good` at or under the target;
   - `amber` up to 1.5× the target;
   - `red` above that.

   **Words:** "Not enough data", "No wins yet", "No target set". Good is green, amber is amber, red is red, and the other three are gray.
10. **Funnel API** (`analytics:read`): `GET /api/v1/analytics/funnel?period&practice&offer&batch` returns:
    ```
    { period: { key, from, to }, stages: [{ key, name }], target_cost_per_won_cents,
      totals: { sent, sources, won, won_pct, spend_cents, cost_per_won_cents },
      rows: [{ source_id, name, kind, counts: number[], step_pct: (number|null)[], cost_per_account_cents: (number|null)[],
               spend_cents, cost_per_won_cents, status, win_rate_pct }],
      shared_spend_cents, updated_at }
    ```
    - **`step_pct[k]`:** `counts[k] / counts[k-1]`, rounded, and null for the first stage or a zero base.
    - **Win rate:** `win_rate_pct = won / sent`.
    - **Rows:** ordered by sent, descending, then by name.
    - **Totals:** cover every account in the cohort, and `sources` is the number of rows. `totals.spend_cents` is the period's whole ledger spend (every source plus Shared costs), and `totals.cost_per_won_cents` = that spend / `won`.
    - **`updated_at`:** the latest `journey.updated_at`.
    - **Data limits:** the cohort is narrowed by the caller's data limit (`filterVisibleAccountIds`), so a seller with `own_accounts` sees only their own.
    - **Spend fields without `costs:read`:** `spend_cents`, `cost_per_won_cents`, `cost_per_account_cents`, `status`, `shared_spend_cents` and `target_cost_per_won_cents` are null. Spend is the period's spend for the source (Ruling 6), never narrowed by data limits.
11. **Drill API** (`analytics:read`): `GET /api/v1/analytics/sources/{id}/performance?period&practice&offer&batch` returns:
    - The source (`name`, `kind`), `rank` and `of`, and `prev_id` and `next_id` (neighbours in the funnel rows' order).
      - The rank is among rows with a `cost_per_won_cents` and sent ≥ 10, lowest cost first. It is null otherwise.
    - Totals `{ sent, won, won_pct, all_won_pct, spend_cents, cost_per_sent_cents, cost_per_won_cents, status }`.
    - `insight`:
      - "Too early to judge." when sent < 10;
      - else "Most accounts stall between {a} and {b}.", for the step with the most losses (`counts[k-1] - counts[k]`), the earliest on a tie;
      - else null.
    - `stages[{ key, name, count, all_count, moved_on_pct, all_moved_on_pct, lost, cost_each_cents }]`.
    - `batches[{ batch_id, name, sent, won }]`, from intake's batch names.
    - `won_accounts[{ account_id, name, offer_name, value_cents }]`:
      - `value_cents` is the sum of won deal amounts, or null when none has an amount.
      - Ordered by value, highest first.
      - Names come from the accounts module and offers from the offers module.
    - **404** for an unknown or removed source. Spend fields follow Ruling 10.
12. **Costs R3b** (`costs:read`):
    - **New summary fields:** `/costs/summary` adds `cost_per_sent_cents`, `cost_per_won_cents`, `return_ratio` and `target_cost_per_won_cents`, all over the last 90 days.
      - Spend is the ledger total.
      - Sent counts journeys that arrived in those 90 days.
      - Won counts journeys that first reached the won stage in those 90 days.
      - **Return:**
        - `return_ratio = won value / spend`, rounded to 1 decimal.
        - Won value is the sum of amounts of won deals with `closed_at` in the 90 days.
        - Null when spend is 0.
    - **New route:** `GET /api/v1/costs/by-source` returns rows `{ source_id, name, kind, spend_cents, share_pct, per_sent_cents, per_assigned_cents, per_won_cents, return_ratio }` for the top-level sources with spend or accounts in the last 90 days, ordered by spend, descending. It then adds one `{ source_id: null, name: "Shared costs", spend_cents, share_pct }` row, plus `total_spend_cents`.
      - A `per_*` value is null when its count is 0.
13. **Sources page.** `GET /api/v1/sources/stats` keeps its shape (`sent`, `reviewed`, `assigned`, `won` and the percentages), but the route now fills it from journeys per Rulings 3 and 4, for all time.
    - **Reviewed:** reached the second flow stage.
    - **New fields `spend_cents` and `cost_per_won_cents`:** all-time spend (Ruling 6, rolled up) and spend / won. Both are null without `costs:read`, and `cost_per_won_cents` is also null with no wins.
    - **The tile:** reads "Not tracked" when `spend_cents` is 0, "None yet" when won is 0, else the money.
    - **Source page:** shows the Cost per win tile, and `See in funnel` opens `/funnel/{id}`.
14. **Backfill.**
    - **Command:** `scout backfill-journeys <slug>` (entry CLI) fills journeys for every account from intake's resolved arrivals, routing's `stage_change` history, the accounts summary (practice and offer) and crm deals.
    - **Re-running:** running it twice changes nothing.
    - **Exports it needs:**
      - intake `listResolvedArrivals(ctx)` returns `{ accountId, closestSourceId, batchId, resolvedAt }[]`;
      - routing `listStageHistory(ctx)` returns `{ accountId, toStage, at }[]`;
      - crm `listDeals(ctx)` returns `{ accountId, system, externalId, status, amountCents, closedAt, syncedAt }[]`;
      - accounts `listScoringPicks(ctx)` returns `{ accountId, practiceId, bestOfferId }[]`.
15. **Not in R3b-1:**
    - Funnel views: the activity view, any-source mode, grouping by practice, offer, batch or seller, and the level switch.
    - Stage detail: time in stage, and drill-down lists behind each count.
    - Exports and tools: CSV export, the MCP tool, and the rebuild/republish job.
    - Cost targets: hours, and batch, practice or offer targets on lines.
    - Also deferred: the seller's own cost per won, and source trust (R3b-2).

## Review Focus

1. **Events out of order or twice.** A redelivered or late `stage.changed`, `arrival.resolved` or `deal.changed` must not move an earlier entry, double-count or bring back an exit. Task 1 tests "a late stage event keeps the earlier entry" and "an older deal event is ignored".
2. **A skipped stage.** An account that jumps from Sent to Assigned counts as Reviewed (Task 2 test).
3. **Shared costs add up.** The per-source spends plus Shared costs equal the ledger total for the period, including voided lines left out and lines on accounts outside any source (Task 2 and Task 3 tests).
4. **A seller.** On the funnel a seller sees only their own accounts, every spend field is null, and `/costs/by-source` is 403 (Task 4 test).
5. **Renamed or deleted stages.** A stage renamed after accounts entered it keeps its counts under the new name. A deleted stage's entries are ignored without breaking the columns (Task 2 test).
