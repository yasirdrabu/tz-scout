## 3. CRM module

- **Fixed tasks**: pure `buildTasks` in src/modules/crm/domain/tasks.ts (first touch due 17:00 tenant tz on handoff day; follow-ups at settings days 3/7/14, from `pkg.firstTouch`/`pkg.followUps`). Task owner = `sellerOwner` (crmOwnerId of handoff seller), person = primary buyer.
- Adapter (src/modules/crm/contracts/adapter.ts:99-112): `upsertTask({externalId?, companyExternalId, personExternalId?, subject, body, ownerExternalId, dueAt}) -> {externalId, status}`; `closeTask({externalId, note?}) -> {status}`. A completed task is never reopened and no new one is made when an externalId is passed (mock.ts:271-293, live.ts:456-490). To recreate for a reopened step call upsertTask without externalId. - `crm.task_link` (db/schema.ts:215): PK (tenant, system, step_id), external_task_id, due_at, status default 'open'. **Nothing writes it.** Only reader: services/follow-through.ts:105 (resolves `stepId` for a `task_done` observation by external task id; no index on external_task_id).
- `crm.link` (scout_type 'task') also holds the fixed tasks; `getLinks` (services/links.ts:~55) and `syncFollowThrough` (follow-through.ts:~60-72) and undo (undo.ts:~255) select tasks by `scoutId` prefix `<assignmentId>:`. - **activity.observed production** (services/follow-through.ts `syncFollowThrough`, `observe`): inserts `crm.activity` (unique tenant,system,externalId) then publishes. Kinds `email|reply|call|meeting` come from adapter `listActivities` (id = CRM activity id, `actorOwnerExternalId` -> `actorUserId` via `userForCrmOwner`); `task_done` is synthesized when a polled task turns COMPLETED (id = the task externalId, occurredAt = now, owner null, `taskExternalId` set, `stepId` from task_link or null). - Mock HubSpot (adapters/hubspot/mock.ts, tables schema.ts:345): `mock_task(tenant, external_id, company_external_id, person_external_id, subject, body, owner_external_id, due_at, status open|completed)`, `mock_activity`, `mock_company`, ... - **Ordering**: handoff runs on `routing.assignment.created` (queueHandoff, handoff.ts:49) and usually finishes in seconds; plan starts on `accepted` (seller response, auto-timeout, or CRM activity), usually later, but can be before the push finishes (CRM-activity acceptance, or fast accept). So both orders occur.
  - Plan first, handoff not yet complete: no company external id yet -> plan sync must wait (defer to end of `runPush`, or retry job); push must skip the fixed tasks when the account has an open plan.
  - Handoff complete, plan arrives: sync closes the open fixed tasks (links `<assignmentId>:first_touch|follow_up:*`, status open in CRM) with a note like "Replaced by the playbook", leaves done ones, creates plan tasks.
  - Re-push (`isRepush`) and a later plan end: push must not recreate fixed tasks once the account has (or had) a plan for that assignment; after the plan completes/stops/abandons tasks are closed and fixed tasks do not return.
  - Pause (withdrawal) closes plan tasks; resume must create fresh tasks (completed tasks cannot reopen) and move owner to the new seller.
- Task body for email steps: subject = step title or draft subject? Spec says the task carries the draft subject/body (AE sends). Use task subject "Email: {subject}" or step title (decide), body = draft body; for other channels body = step detail. Plain text vs HubSpot html: `esc()` helpers exist in live.ts; check note builder for html escaping conventions.
- Due date: step `due_date` is a date; HubSpot tasks use instants at 17:00 tenant tz (`dueOn` in tasks.ts, private; export or reuse `wallClock/offsetAt` from `@/platform/time`).
- Owner: step owner_user_id -> `crmOwnerId(ctx, userId, system)` (tenancy/index.ts). Operator steps have no owner and sellers without a CRM owner are possible: fall back to plan seller; if none, no owner.

## 4. Module boundaries

- ESLint (eslint.config.mjs:12-34): module code may import another module only via `src/modules/*/index.ts` or `contracts/**`. No import-cycle check exists. Today playbooks imports crm and routing; crm and routing import nothing from playbooks. crm and routing already import each other's `contracts/events`.
- CRM <- plan data. Options: (a) event payloads: extend `plan.created/changed` with channel, subject, body, detail, order, day, ownerUserId, status, crmTask, target person ids for every touched step, and CRM keeps its own step table; fragile with ordering (events of different types are not ordered, only per account within one consumer). (b) **Port (recommended)**: `PlanTaskProvider.planTasks(ctx, accountId)` defined in `crm/contracts/ports.ts` next to `HandoffPackageProvider`, implemented by playbooks and registered in `src/entry/compose.ts:27`. Events only trigger a `crm.plan.sync` job (consumers on plan.created, plan.changed, step.completed in crm/consumers.ts, importing `@/modules/playbooks/contracts/events`, allowed by lint and matching how routing imports crm events); the job reads the whole current plan (status, steps incl. drafts, owners, due dates) and reconciles with `crm.task_link`. Idempotent, order-proof, one place handles pause/stop/abandon. spec crm-sync/index.md:100 already says "step data read from the package provider"; `HandoffPackage.planSteps` (crm/contracts/types.ts:49, always `[]` in playbooks/domain/package.ts:187) is the stub for the same idea and the push can use it to skip fixed tasks.
- Playbooks <- CRM activity: playbooks consumer of `crm.activity.observed` (import from `@/modules/crm/contracts/events`, allowed). Needs a system-level step-done function (updateStep requires visibility and uses `ctx.actor.id`); `done_by` for CRM completion = null or actorUserId (event actor is null for task_done).
- Routing <- playbooks: routing must not import playbooks. The needed event has to be defined somewhere both can see. Either (a) routing consumer imports `@/modules/playbooks/contracts/events` (contracts only, same pattern as routing->crm, creates a contract-level cycle with playbooks->routing) or (b) the owner prefers zero imports: define the event def in playbooks and have `compose`/worker bind it, which the code has no mechanism for. Recommend (a); tell owner.
