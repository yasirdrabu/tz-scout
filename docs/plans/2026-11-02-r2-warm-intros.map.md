### Key gap: stored points go stale
`warm_intro.points/effective_points` are written once at declare time. Editing a rule/default does not change them, and getWarmIntro reads them. A rescore alone would not change scores. Plan must either (a) recompute and update warm_intro rows (full points via warmIntroFullPoints with current rules/defaults, effective via warmIntroPoints with row.confirmed) for affected rows when rule/default/confirm changes, then rescore; or (b) compute in getWarmIntro. (a) matches "canonical model; Scoring keeps no points". Confirming must update `confirmed=true`, `effective_points=points` (or recompute), `confirmed_by`.

## 9. Open questions / gaps
1. Stale stored points (see section 2): choose recompute-and-update of warm_intro rows vs compute-on-read. Also what "affected accounts" means for default edits (rows using that default, i.e. no overriding rule).
2. `intake.source.trust_changed` needs a sourceId (person source) and level; outside (email-only) introducers have none; arrival-sender-based `accountIdsForSource` does not map to introducer. Likely the plan should rescore by explicit account id list (new RescoreFilter field like `accountIds`, or call `rescoreAccounts`) while still publishing the spec event, or publish a dedicated event. Decide what the trust_changed consumer does for cause 'warm_intro_points' (today it rescores by sourceId with cause 'trust_changed' regardless of cause; payload `from`/`to` semantics for points). Spec says SCO-E2-S2-AC2 allows "a dedicated SRC event".
3. `intake.warm_intro.confirmed` payload and SCO consumer (rescore that account with cause 'warm_intro') both new; `scoringConsumers` list and worker registration need updating; event catalog already lists it.
4. Rules UI needs a rule model with an id (no PK now); no create/update/delete service; introducer picker (tenant user vs outside email) and relationship key; uniqueness conflicts (two partial unique indexes).
5. "Owner" mapping: use `settings:manage` (owner-only by default) vs `scoring:manage` (owner+operator). Spec screens list is by permission; decide. GET currently platformAdminOnly; must change both GET and PUT, and update stale comment in [key]/route.ts.
6. Confirm authorization: reviewers = `review:act`; named introducer = user matching warmIntro.introducerUserId (any tenant member, even without review:act). v1Route supports a single permission, so a service-level check is needed. Also is an agent/vendor-declared intro on an account the introducer cannot see (data scopes) confirmable? Needs `accounts:read` visibility check.
7. Score read lacks confirmed/fullPoints/warm_intro id/introducer_user_id; explanation line text for unconfirmed ("Unconfirmed, +4 of 8") is not produced; decide whether to extend explainScore (scoring depends on intake index only) and the explanation line label (playbooks/inputs.ts:123 and tiles.ts:43 parse the label "Warm intro from X", so changing it breaks parsing).
8. No mockups for any of the three features; screens.md needs new section (21i) and api-gaps rows; web-ui nav entry/permission and `SCREENS` registration; copy must be invented from spec strings.
9. confirmedBy format `kind:id` (actor), no confirmedAt; the multi-intro rule "highest counts" means confirming a non-strongest intro may not change score.
10. Idempotency/double confirm: confirming an already confirmed intro should be a no-op without a second event.
