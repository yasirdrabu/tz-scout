## 6. Conventions summary
- Events `<module>.<entity>.<past_verb>` (accounts.conflict.detected/resolved), `defineEvent(type, 1, zod)`, publish in the same tx via outbox; consumer names `<module>.<what>`; register in entry/worker.ts:27; event files in entry/registry.ts.
- Ids `newId('<prefix>')` (platform/ids); conflict prefix `cfl_` (accounts/index.md:44).
- Errors `ScoutError({slug, status, title, errors?})`; 404 for hidden/missing; 409 slug 'conflict' for stale state (e.g. conflict already resolved, kept fact not in the conflict -> 400 validation).
- Routes: `v1Route({permission, peopleOnly?})`, snake_case output automatically (v1-route.ts snakeCase), `idAndAction`, `parseBody(req, zod.strictObject)`, `pageOfList` for lists; POSTs idempotent by `Idempotency-Key` by default.
- web-ui: `apiFetch<T>(path, {tenant, method, body})` (api/client.ts:66, POST sends Idempotency-Key); `queryOptions` with keys `['account', tenant, id, '<part>']`, `['review-queue', tenant, ...]`; invalidate by prefix after mutations; msw fixtures in features/*/testing.ts; vitest + Testing Library; copy from the API (C6-C8).
- Tests: unit tests/unit/<module>/, integration tests/integration/<module>/ and tests/integration/v1/ (route-level, `w.as(principal, handler, path)` helpers in v1/*-helpers.ts), e2e tests/e2e/*.spec.ts. Commands: `npm run test:unit`, `npm run test:int`, `npm --prefix web-ui test`, `npm run e2e`.

## 7. Open design questions
1. Tolerance settings: no Settings screen or table exists and screens.md specifies none. Proposal: defaults only, in code (domain), editable later.
2. Default rule for keys the table does not list (name, domain, hq_city, hq_state, seniority, founded_year, researcher_score, form.*, linkedin_url, parent_domain ...): never conflict, or "different value"? And `employees_min/max` (range) vs `employees` (count) are separate keys; range overlap needs both keys from one chain.
3. Which money threshold applies to `price_cents`, `revenue_min/max_cents`, `budget_cents` (spec names only revenue 25%, "other money" 10%).
4. Trust drop of 0.01 on a lost conflict: SRC-E1-S3-AC2 is in the R3 story and nothing writes `source.trust`; R2 = feedback row only, or also write trust (which then moves effective trust off 0.60 and, at < 0.02, publishes no trust_changed)?
5. `conflict_explanation`: catalog says the output names "which looks more current" and a rules fallback "newer and higher-trust first"; ACC says it "never picks a winner". Also: is the rules fallback shown when no key (mode rules), given mock shows nothing?
6. A source re-sending a value that lost (archived) is stored again as a new candidate and would reopen the conflict on every arrival. Ignore values matching an archived fact from the same chain?
7. "Kept by {name} · Change": re-resolving a resolved conflict (switch the pin) is not in the API spec. Allowed?
8. A person's edit of a key with an open conflict: close it as resolved by the edit, or leave it open against the new pin?
9. Existing data: backfill conflicts from current candidate facts (one-off job) or only detect on new arrivals?
10. Queue `flag=conflicts`: via accounts' summary count (immediate) or routing's REVIEW_FLAGS per REV spec (async)? Low-trust flag is out of scope?
11. Rescore progress: count shown is tenant-wide (not data-limited) - acceptable for `review:act`? Several concurrent runs (rules + offer): show the latest, or sum the active ones?
12. Estimated value: currency of the estimate (offers store cents only; USD?), and whether the CSV export shows it.
13. Warm intros: R2 items exist (confirm flow, rules editing + rescore) but have no screens.md section. In R2a or a later plan?
